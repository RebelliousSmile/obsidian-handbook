# Plan: Superviseur plus rapide, vérifications par contenu et par rôle

## Overview

| Field  | Value |
| ------ | ----- |
| Goal   | Réduire la durée d'un train en supprimant les rejeux inutiles et les découvertes tardives, et remplacer les égalités de littéraux (SHA, version, épingle) par des vérifications sur le contenu et sur le rôle, sans toucher aux invariants de publication. |
| Source | Demande de l'utilisateur du 2026-10-07 (« analyse le fonctionnement des skills et des commands supervisor pour voir où on perd du temps, et si on peut avoir plus de souplesse dans les vérifications plutôt qu'un alignement bête et méchant »), et le diagnostic livré dans la même conversation sur le dernier train PbtA : vingt cycles `ship` en quatre heures environ, dont quatre cycles de 17 à 20 minutes soldés par un échec. |

## Phases

| #   | Phase | File |
| --- | ----- | ---- |

| 2 | Présenter les consommateurs contre l'archive empaquetée du fournisseur | [phase-2.md](./phase-2.md) |
| 3 | Répéter en local les preuves statiques du train avant tout dispatch | [phase-3.md](./phase-3.md) |
| 4 | Gardes écrites par rôle, plus par littéral | [phase-4.md](./phase-4.md) |

| 6 | Re-présentation par contenu : ne rejouer que ce qui a changé | [phase-6.md](./phase-6.md) |

## Decisions

| Decision | Why |
| -------- | --- |
| L'ordre des phases suit le rapport gain sur risque : d'abord rendre les échecs lisibles (1), puis avancer leur découverte (2, 3, 4), puis seulement assouplir des égalités (5, 6). La phase 7 se fait après la phase 5, sans attendre la phase 6. | Les phases 1 à 4 ne retirent aucune vérification : elles les déplacent plus tôt ou les rendent lisibles. Les phases 5 et 6 changent ce qui fait foi ; elles s'appuient sur les empreintes de contenu que la phase 2 introduit. |
| **Confirmée par l'utilisateur le 2026-10-07** : un candidat reste celui du train tant que le commit lié du fournisseur descend du commit dont il a été tiré et que le contenu empaqueté du fournisseur n'a pas changé entre les deux (phase 5). | Une re-présentation lie le fournisseur à son nouveau `HEAD`. Le candidat enregistré est conservé (`settleCandidate`), mais `adapters/pbta.mjs` indexe sur le commit lié les inputs des workflows, le filtre des manifestes et le reçu du digest : les runs déjà verts sont redispatchés et le manifeste re-posé, alors que les octets du candidat n'ont pas bougé. Les workflows du fournisseur acceptent déjà un commit antérieur à `main` (extraction du commit reçu, ascendance vérifiée). Le critère est l'empreinte empaquetée, pas les `trainFiles` : les correctifs du dernier train touchaient des scripts du fournisseur hors paquet, qu'un critère par `trainFiles` aurait refusés. C'est une décision de conception : elle change la définition de « même candidat ». |
| **Confirmée par l'utilisateur le 2026-10-07** : le résultat vert d'un dépôt est réutilisé à la re-présentation quand son arbre git, le contenu empaqueté de ses fournisseurs, ses commandes de validation et la version de Node sont identiques (phase 6). | Aujourd'hui tout commit hors `trainFiles` dans un seul dépôt relance les validations de tous. Ce que chacune rejoue vraiment n'est pas mesuré : les sorties du dernier train sont tronquées à trente lignes, et `check.mjs` reprend déjà un `pnpm check` de Handbook sur contenu identique. La phase 6 commence donc par ce relevé, que la phase 1 rend possible, et s'arrête s'il ne montre pas de gain. La clé porte sur le contenu, pas sur l'heure ni sur le SHA. Le gain vise les consommateurs : un dépôt modifié est toujours rejoué, puisque son arbre entre dans sa clé. La reprise exige un checkout propre. L'adoption validée n'est pas concernée : verte, elle est commitée et n'est pas rejouée ; rouge, elle n'est jamais reprise. C'est une décision de conception : elle change ce que « présenté » veut dire. `--fresh` rejoue tout. |
| Chaque phase se termine par le commit et le push du code du superviseur sur `origin/main`, et aucun train n'est lancé ni en cours pendant le travail d'une phase. | `self.mjs` refuse `ship` tant que le code du superviseur diffère d'`origin/main` ; ce refus reste. Un module neuf sous `tools/supervisor/` est couvert d'office par `SELF_PATHS` ; `tools/checkRun.mjs` et `tools/assert-guards-by-role.mjs` n'en font pas partie, ce sont des portes de `check`. Le commit et le push restent soumis à la demande de l'utilisateur. |
| Tout champ ajouté à l'enregistrement d'un train est facultatif, et un enregistrement écrit avant la phase se lit avec le comportement d'avant. | Un train ouvert avant une phase doit pouvoir se fermer après elle ; le schéma `train.schema.json` refuse les champs inconnus, il est donc étendu dans la même phase que le code. |
| La présentation contre le paquet (phase 2) répond à un échec constaté, pas à une hypothèse. | Au dernier train PbtA, l'adoption du candidat a échoué sur un dossier présent dans le checkout du fournisseur et absent de son archive : `present`, qui copie le checkout entier, l'avait laissé passer. |
| **Faisabilité constatée le 2026-10-07 (phase 2)** : le moyen retenu est `npm pack --dry-run --json`, lancé derrière la garde dans le checkout de chaque fournisseur ; aucun des replis prévus n'est nécessaire, et aucune empreinte n'est « partielle ». | Relevé sur les trois fournisseurs, deux passages chacun. `schema-pbta` : code de sortie 0, 390 fichiers listés, `prepack` (build puis génération) exécuté et écrivant des lignes sur la sortie standard avant le JSON, `git status` vide après coup, mêmes octets aux deux passages, environ 5 s. `schema-adrenaline` : code 0, 186 fichiers, `prepack` exécuté de la même façon, checkout propre, stable, environ 5 s. `schema-in-the-mist` : code 0, 201 fichiers, pas de `prepack` (son build séparé est donc conservé), sortie JSON seule, checkout propre, stable, environ 1 s. La commande ne publie rien et la garde ne la refuse pas. Les nombres de fichiers sont ceux du jour du relevé. |
| Le listing de `npm pack --json` est lu depuis la dernière ligne qui ouvre un tableau, pas depuis le début de la sortie. | Deux des trois fournisseurs écrivent sur la sortie standard depuis `prepack` avant le JSON : un `JSON.parse` de la sortie entière échouerait. |
| Tout fournisseur que le train change est empaqueté, même si aucun consommateur présenté ne l'installe ; l'empaquetage tourne avant les validations propres du fournisseur ; le repli « lier le checkout entier » est supprimé. | L'empreinte s'écrit à côté du commit du fournisseur, où les phases 5 et 6 la liront : elle ne doit pas dépendre de la présence d'un consommateur. Le repli aurait rouvert l'écart que la phase ferme. Un paquet installé hors d'un `node_modules` reçoit la même copie, sans frères. |
| L'empreinte est locale à la machine et ne se compare qu'entre deux présentations. | Elle hache les octets du checkout, qui suivent ses fins de ligne ; l'archive de la CI est produite sous Linux. La comparer au `sha256` d'un candidat fabriquerait des écarts. |
| **Trou du tampon de `check` constaté par lecture, puis fermé.** Le tampon `full` hache le checkout suivi ; le fournisseur lié vit sous `node_modules`, hors de ce hachage. | Un `pnpm check` vert sur l'épingle aurait été réutilisé sous `present` contre un fournisseur différent. `present` exporte `SUPERVISOR_LINKED_PROVIDERS` (fournisseur et empreinte) aux validations des consommateurs réellement liés, et `check.mjs` le mêle au tampon ; sans fournisseur lié le tampon est inchangé, donc les verts existants tiennent. Prouvé par `assert:check-run` sur le module pur, pas par un `check` réel sous `present`. |
| Restent stricts, sans exception : octets du final égaux à ceux du candidat (`sha256`), épingles finales exigées à `converge`, garde de publication (`guard/`), version d'un consommateur jamais déjà publiée, `pnpm install --frozen-lockfile`. | Ce sont les invariants de publication. La souplesse demandée porte sur la manière de reconnaître un contenu déjà prouvé, pas sur ce qui est publié. |
| Un échec rouge n'est jamais réutilisé ; seul un résultat vert l'est. | Une réutilisation ne doit pouvoir que faire gagner du temps, jamais masquer un rouge ni en fabriquer un. |
| Le mode collecte de `check.mjs` ne démarre pas `assert:supervisor` quand une autre porte est déjà rouge. | Ce harnais dure plus de treize minutes à lui seul (mesuré) ; le lancer derrière un rouge connu allonge le cycle sans rien apprendre. Il est rapporté « non lancé », jamais « vert ». |
| La répétition locale (phase 3) couvre les preuves statiques du manifeste et l'ascendance ; la preuve sur hôte Obsidian reste en CI. | `release-train.yml` provisionne une AppImage Linux sous `xvfb` : elle ne se rejoue pas sous Windows. Classement fait : les trois runs rouges du dernier train PbtA ont tous échoué à l'étape « Validate immutable release-train input », avant l'hôte Obsidian. Cette étape lance la validation statique du fournisseur, qui ne lit que trois fichiers du checkout (manifeste de train, enregistrement du candidat, enregistrement de stage) : elle se répète en local, et la répétition aurait évité ces trois allers-retours. |
| **Faisabilité constatée le 2026-10-07 (phase 3)** : la preuve statique de `schema-pbta` se rejoue telle quelle en local ; aucun script neuf n'est demandé au fournisseur. | Relevé dans un checkout propre du fournisseur, sous Windows : `npm run validate:release-train -- <manifeste de train>` sort en 0 en moins d'une seconde et laisse `git status` vide. Elle lit le manifeste passé en argument, l'enregistrement du candidat sous `release-train/candidates/`, et l'enregistrement de stage seulement s'il existe ; ni réseau ni dépôt consommateur. Elle a besoin des dépendances installées du fournisseur. Un manifeste absent donne une erreur qui nomme son chemin. Après elle, `release-train.yml` vérifie l'ascendance de `provider_commit`, puis démarre l'hôte Obsidian. |
| La répétition se déclare dans la topologie (`rehearsal` d'un fournisseur, jeton `{manifest}`) ; l'adaptateur ne fait que marquer les pas qu'elle précède. | Le superviseur ne connaît le nom d'aucun script d'un fournisseur. Une commande de répétition sans le jeton est refusée à la lecture de la topologie, comme une `rehearsal` sur un consommateur : une répétition qui ne lit pas le manifeste qu'on lui donne ne prouve rien de lui. Champ facultatif, schéma étendu dans la phase. |
| La répétition tourne à deux pas : avant de poser le manifeste de train, et avant de dispatcher `release-train.yml`. Le manifeste candidat n'est pas répété. | Le premier évite de commiter sur `main` un manifeste que le workflow refuserait ; le second couvre la reprise, quand le manifeste est déjà posé et que le dépôt a bougé depuis. La validation statique du fournisseur porte sur le manifeste de train : aucun des runs rouges classés ne portait sur le manifeste candidat. |
| Avant d'être posé, le manifeste est écrit dans le checkout le temps des commandes puis retiré ; un checkout laissé modifié par une répétition verte est un échec. | La validation lit un fichier, pas un contenu passé en argument. Le pas qui pose le manifeste exige un checkout propre et le réécrit lui-même : rien d'écrit par la répétition ne doit lui survivre. |
| L'ascendance est vérifiée par la répétition elle-même, sur le commit que l'adaptateur passe au workflow, en plus de la liaison de présentation. | La liaison vérifie déjà qu'`origin/main` descend du commit présenté. La répétition refait le contrôle du workflow sur son entrée exacte, pour ne pas dépendre de ce que les deux commits restent le même. Prouvé par une sonde directe du module, la liaison rendant le cas inatteignable par la commande. |
| Les deux répétitions d'un même `publish --run` écrivent le même fichier de journal (`<fournisseur>-1-rehearse.log`). | Le rang repart à chaque répétition. Seule la dernière sortie est gardée : une répétition rouge arrête la commande, c'est donc toujours la sienne. Les durées, elles, gardent une ligne par répétition. |
| **Inventaire des gardes (phase 4, relevé le 2026-10-08)** : aucun script de garde n'est empaqueté. | `tools/` est absent du champ `files` des trois fournisseurs (lu sur leur `origin/main`). Les réécritures hors Handbook restent donc dans cette phase, hors train. Commandes relevées : Handbook `pnpm check` et, en convergence, `assert:consumer-schema-pins -- ../lantern/package.json --final` ; Lantern `lint`, `typecheck`, `assert:release-train`, `assert:release-identity`, `assert:release-train-matrix:unit`, `assert:consumer-schema-pins:unit`, `assert:workspace`, et en convergence `assert:consumer-schema-pins -- ../obsidian-handbook`, `assert:release-inputs`, `assert:release-train-matrix` ; les trois fournisseurs `npm run check`. |
| Inventaire : les trois gardes cassées par le dernier train PbtA sont déjà corrigées par rôle. | Handbook `tools/assert-release-train-schema-pbta.mjs` liait la preuve à l'épingle courante ; elle exerce maintenant une archive fermée pour elle-même. Handbook `tools/pbtaPackCoverage.harness.mts` lisait le dossier `handbook` du fournisseur, absent de l'archive ; il lit les contrats d'apparence publiés. Fournisseur PbtA `tools/validate-handbook-install.ts` refusait un candidat staged comme épingle Handbook ; il l'accepte. |
| Inventaire : trois gardes figent encore une valeur que le train déplace. | **Handbook** `tools/assert-release-train-schema-adrenaline.mjs` : URL d'archive d'un candidat, sha256, integrity et version installée écrits en littéral, alors que l'épingle a avancé depuis. Elle est nécessairement rouge, exclue de `pnpm check` (porte réseau) et lancée par aucun workflow : garde morte. **Fournisseur PbtA** `tools/validate-package.ts` : compare `PBTA_CONTRACT_SCHEMA_TAG` à un tag écrit en littéral, alors que `src/contract-version.ts` le déclare. **Fournisseur PbtA** `tools/validate-handbook-packs.ts` et `tools/validate-handbook-install.ts` : `minimumHandbookVersion` attendu en littéral. |
| Inventaire : le reste est donnée de test fermée, à marquer et non à réécrire. | Handbook : `assert-release-train-schema-pbta.mjs` (archive exercée, tag candidat, versions d'Obsidian), `release-train-schema-pbta-assert.mjs` (version d'Obsidian), `assert-release-train-schema-in-the-mist.mjs` (tag nul), `pbtaPackCoverage.harness.mts` (versions de packs inventés), `assert-release-train-protocol-1.mjs` (manifestes synthétiques, hors table). Lantern : harnais `consumer-schema-pins`, `release-identity`, `release-train-matrix`, `release-train-protocol`. Fournisseur Adrenaline : `assert-final-release.ts`, `assert-release-train.ts`, `validate-versioning.ts`, `verify-*.ts`, `write-release-train.ts`. Fournisseur Mist : `test-release-train-*.ts`, sur un manifeste historique. |
| Inventaire : aucune garde ne dépend de l'étape du cycle. | Rien trouvé qui ne puisse décider par ses arguments ou les fichiers qu'elle lit. La tâche 2.4 est sans objet. |
| Le détecteur vit dans un module pur `tools/guardsByRole.mjs`, troisième fichier hors de la projection. | Le harnais doit importer le détecteur sans lancer le lanceur, comme `checkRun.mjs` pour `checkRun.harness.mts`. Le module porte aussi `finalPin`, le rôle « release finale qu'un consommateur épingle », lu dans `package.json` et `pnpm-lock.yaml`. |
| Marqueur de fixture : `guard-fixture: <raison>` sur la ligne même ; un marqueur sans raison n'admet rien. | La raison oblige à dire pourquoi le chiffre est fermé. Une ligne de commentaire seul n'est pas lue : un commentaire ne compare rien. Une adresse à quatre composantes n'est pas une version. |
| Une garde affirme un rôle (« la version que `package.json` déclare », « le candidat que le train observe »), jamais un littéral de version, de tag ou de SHA. | Plusieurs gardes ont cassé parce que le train déplaçait précisément la valeur qu'elles figeaient. La règle rejoint celle des plans : désigner par rôle. |
| Aucune variable d'environnement n'expose l'étape du cycle aux gardes. | Recherche faite dans les cinq dépôts : aucun script ne lit `SUPERVISOR_PRESENT`, et la garde d'épingle de Handbook reçoit déjà `--final` par sa commande de convergence. Les trois gardes cassées au dernier train figeaient un littéral ; aucune ne devinait une étape. Une garde qui en aurait besoin la reçoit par un argument de sa commande dans la topologie. |
| La phase 6 attend un train réel livré après les phases 1 et 2 : son relevé se lit dans le résumé des durées de ce train. | Aucun train ne tourne pendant le travail d'une phase, et le relevé ne se fabrique pas sur un monde de test : ce sont les durées réelles des cinq dépôts qui décident. La phase 1 conserve ce résumé à la clôture pour cela. |
| Les harnais qui prouvent ces changements restent `tools/<nom>.mjs` + `tools/<nom>.harness.mts`, et les scénarios du superviseur restent dans `tools/supervisor.harness.mts`. | Règle du dépôt : pas de vitest ni de jest, aucune dépendance neuve. |
| La logique de `check.mjs` est extraite dans un module pur (`tools/checkRun.mjs`) pour être prouvée avec un lanceur factice. | `check.mjs` calcule sa racine depuis son propre emplacement et lance de vrais scripts : sans extraction, sa preuve relancerait `pnpm check` dans `pnpm check`. |
| Paralléliser les scénarios de `assert:supervisor` est hors de ce plan. | Le gain est réel (chaque phase de ce plan touche le superviseur et paie donc ce harnais) mais indépendant du diagnostic ; à ouvrir comme un plan à part. |
| La décision « le code du superviseur n'est jamais commité par `ship` ; sa relecture reste humaine » du plan `supervisor-without-approve` est abrogée ; la skill est alignée en phase 7. | Règle retirée par l'utilisateur le 2026-10-07 : le diff du superviseur ne demande plus d'accord. `ship` refuse toujours de tourner sur un code de superviseur non publié (`self.mjs`) : ce refus-là reste, seul son message, qui nomme « une personne », est reformulé en phase 7. |
| Les modifications dans Lantern et les paquets `schema-*` (phase 4) sont des commits d'outillage, hors contrat publié. | Elles touchent des scripts de validation, pas le contrat ni la sémantique de présentation ; le flux inter-dépôts (étendre le schéma, le publier, l'adopter) ne s'applique pas. Vérifié pour le fournisseur PbtA : son champ `files` ne publie pas `tools/`. À vérifier de la même façon pour chaque autre dépôt touché, en tâche 1 de la phase 4. |

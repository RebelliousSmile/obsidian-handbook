# Plan: Équipement et actions de départ conformes aux règles (Monsterhearts, Urban Shadows)

## Overview

| Field      | Value |
| ---------- | ----- |
| **Goal**   | Remplacer, pour Monsterhearts et Urban Shadows, les champs génériques `startingMoves` et `gear` (forme PbtA commune) par des formes qui correspondent aux règles de chaque jeu, puis faire suivre Lantern et Handbook. Changement cassant côté schéma : une majeure. |
| **Source** | [schema-pbta#51](https://github.com/RebelliousSmile/schema-pbta/issues/51) « Monsterhearts et Urban Shadows : startingMoves et gear conformes aux règles ». Le ticket est complet (constat, proposition, hors champ) ; sa mise à jour du 2026-11-09 sur `markedCircles` est déjà livrée et ne fait pas partie de ce plan. |

## Decisions

| Decision | Why |
| -------- | --- |
| **Une majeure du fournisseur (v<N+1>), consommateurs à la suite dans le même train.** Retirer ou remodeler un champ est cassant ; le schéma JSON de la version courante est figé octet pour octet (`validate:version`). Recette de la majeure précédente (constantes de contrat, `archivedVersions`, `package.json`, manifestes, `docs/compatibility.md`, `schemas/v<N+1>` généré). | Précédent des majeures qui ont retiré ou ajouté un champ ; le ticket le demande. |
| **Pas de chemin de lecture de l'ancienne forme dans le schéma.** Un TOML qui porte `startingMoves`, `equipmentType` ou `quantity` pour ces deux jeux est refusé (témoin de refus). Le changelog le dit. | Un schéma peut retirer un champ mal intégré ; seuls les consommateurs ne masquent pas un champ encore déclaré. |
| **`startingMoves` est retiré des deux jeux** (première branche du ticket), pas remplacé par une métadonnée de sélection. | `moves[].checked` couvre déjà l'acquisition ; une seconde voie ferait deux sources de vérité. Conséquence à traiter : les mises en page de Lantern et de Handbook lisaient `move.checked ?? ('ref' in move && startingMoves.includes(move.ref))`. Pour ces deux jeux, le repli par `startingMoves` disparaît ; une action écrite en `{ ref }` sans `checked` est non acquise. |
| **Équipement Urban Shadows : seul `name` est requis, le reste est facultatif.** Chaque ligne du livret reste exprimable : la prose (« une voiture d'occasion ») est un nom nu, l'arme porte dégâts, portée et étiquettes. `equipmentType` et `quantity` disparaissent. | Les livrets mêlent prose et armes ; une forme où l'arme est obligatoire ne saurait pas écrire l'équipement de départ réel. |
| **Dégâts et armure se lisent comme le livret** : dégâts en entier (`n-harm`) ou étourdissants (`s-harm`, sans valeur) ; armure en valeur et mode (base `x-armor` / bonus `armor+x`) ; portée en liste parmi `hand`, `close`, `near`, `far`. La forme exacte des champs (une structure ou deux champs) est fixée à la phase 1 après lecture du chapitre 3, avec cette contrainte : le TOML reste lisible à la main et un témoin de refus couvre « `s-harm` avec valeur » et « armure sans mode ». | Le ticket fixe le sens, pas la forme ; la forme se décide contre le livre, pas de mémoire. |
| **Étiquettes : un vocabulaire publié par le jeu, ouvert à l'ajout.** Le schéma accepte toute étiquette ; la game-definition d'Urban Shadows publie la liste connue (`ap`, `area`, `autofire`, `concealable`, `loud`, `messy`, `reload`, `cherished`, `silver`, `cold iron`, `holy`…) pour que Lantern propose un choix et laisse ajouter. Une étiquette hors liste n'est pas une erreur. | La table peut étendre la liste (livre, « Fictional tags ») ; le contrat de menus pilotés par les métadonnées publiées interdit une liste codée dans Lantern. |
| **Monsterhearts : `gear` se réduit à `name` et `description`.** | Le jeu n'a pas de système d'équipement ; garder `gear` (plutôt que de le retirer) laisse écrire un objet de playbook, comme le fétiche d'une Sorcière. |
| **Les autres jeux gardent la forme générique** (Masks, The Sprawl, Monster of the Week, le livret générique). Seuls les deux jeux visés changent. | Le ticket ne vise qu'eux ; Masks et The Sprawl ont un vrai usage de `quantity` et de `equipmentType`. |
| **Affichage : `9mm Beretta — 2-harm near loud concealable`**, nom, tiret, dégâts, portée, étiquettes, comme le livret ; une ligne de prose s'affiche telle quelle. Les mots de dégâts, de portée et d'armure sont des termes de jeu écrits en anglais sur le livret (`harm`, `near`, `armor`) : ils s'affichent comme le livret, sans traduction. | Cible = le livret ; un terme de jeu déjà validé ne se traduit pas sans demande. |
| **Plan à exécuter après le train `pbta-playbook-render-fixes`** : il touche les mêmes éditeurs (`UrbanShadowsPlaybookEditorPanel.tsx`) et le même contrat ; `supervise open` exige des dépôts propres sur `origin/main`. | Éviter un conflit de train et une base de contrat qui bouge sous la phase 1. |
| **Un seul train pour les trois dépôts**, malgré « dans un train à part » du ticket (qui le distingue du train du `markedCircles`, pas d'un train par dépôt). | La majeure casse les consommateurs : ils doivent être mesurés sur le paquet du fournisseur dans `present`, comme pour les majeures précédentes. |
| **Aucun équipement n'existe aujourd'hui** dans les exemples, témoins et modèles de ces deux jeux (vérifié le 2026-11-24 : `gear` vide côté Lantern, aucune occurrence dans `examples/` ni `corpus/temoins`). Il n'y a donc rien à migrer, seulement des cas à créer. | Évite d'inventer une conversion d'anciennes fiches. |
| Les versions se désignent par rôle (fournisseur v<N+1>, consommateurs v<N+1>), jamais par numéro. | Règle de plan du projet. |
| **Forme fixée à la phase 1 (livre lu le 2026-11-24), élément d'équipement Urban Shadows** : `name` (requis), `description?`, `harm?` (entier ≥ 0 = `n-harm`, **ou** la chaîne `"stun"` = `s-harm`), `armor?` (table `{ value, mode }`, les deux requis ; `mode` = `base` pour `x-armor` ou `bonus` pour `armor+x`), `range?` (liste parmi `hand`, `close`, `near`, `far`), `tags?` (liste de chaînes ouverte). `harm = 2` s'écrit à la main comme le livret ; `armor = { value = 1, mode = "base" }`. | Livre, chap. 3 : « Armor is written out in one of two ways: x-armor or armor+x » (base ne se cumule pas, bonus se cumule) ; `s-harm` n'a pas de valeur ; les armes des livrets s'écrivent `2-harm near loud concealable`, `s-harm hand` (Taser), `2-harm hand stun`. **La portée est une liste** : les livrets impriment `close/near`, `near/far`, `hand/close`. **Pas de `.refine()`** : le contrat interdit les règles croisées (elles ne survivent pas à la conversion en schéma JSON) ; la forme porte donc elle-même l'exclusion : `harm` est une union entier / `"stun"` (un `s-harm` avec valeur est inexprimable) et l'armure est une table dont la valeur et le mode sont tous deux requis (une armure sans mode est refusée). L'étiquette `stun` est une étiquette d'objet distincte (« capable d'infliger s-harm à la place du mal ordinaire ») : `2-harm hand stun` garde `harm = 2` plus l'étiquette `stun` ; seul le Taser (`s-harm hand`) porte `harm = "stun"`. |
| **Vocabulaire d'étiquettes publié (clé `equipmentTags` de la game-definition d'Urban Shadows)** : `anchored`, `ap`, `area`, `autofire`, `booby-trapped`, `cherished`, `concealable`, `exhausting`, `fire`, `fragile`, `loud`, `messy`, `mythic`, `reload`, `reputation`, `silver`, `cold iron`, `holy`, `smoke`, `stun`. Les portées ne sont pas des étiquettes du vocabulaire : elles ont leur champ. | Tableau « ITEM TAGS » du livre (p. 311) ; le livre dit « don't think of the lists as definitive — add it! », d'où une liste publiée mais non fermée. `reputation (circle)` prend un paramètre : on publie `reputation`, la table ajoute le cercle en texte libre. |
| **Constat Monsterhearts** : aucun playbook n'imprime de liste d'équipement dans le volume 1 (édition française) ; les seules choses à noter sont les deux fétiches de la Sorcière (« Vous commencez la partie avec deux fétiches. Décidez de leur nature et à qui ils appartiennent », p. 255 à 257), qui se notent « dans les marges de votre livret ». `gear` = `{ name, description? }` suffit. | Lu le 2026-11-24 ; confirme la ligne « Monsterhearts : `gear` se réduit à `name` et `description` ». |
| **L'équipement de départ des livrets propose des choix** (« une arme au choix : … »). Le schéma n'écrit que ce que le personnage **a retenu** : un élément par objet détenu. La liste des choix imprimés reste du texte de livret, pas des données du schéma. | Le schéma décrit un personnage, pas le livret vierge ; les choix sont déjà le travail du joueur à l'écran de Lantern. |
| **Écart constaté à la phase 1 : le vocabulaire d'étiquettes est publié dans le contrat de présentation d'Urban Shadows (clé `equipment` : 4 portées, 20 étiquettes, libellés fr/en), non dans la game-definition.** | Lantern lit les métadonnées par les contrats publiés (`packs/<jeu>/presentation-contract.json`), pas par la game-definition de l'utilisateur ; la clé `equipmentTags` annoncée plus haut n'existe donc pas. Le schéma d'équipement garde `tags` ouvert. |
